# クロスモデル・レビュー依頼テンプレート（タスク分割案の審査）

`<...>` を埋めてそのまま渡す。`meeting-to-task-ledger` スキルの「クロスモデルレビューの掛け方」から使う。
別モデル CLI への渡し方（サンドボックス指定・非対話実行）は `codex-sol` スキルを参照。

---

あなたに審査してほしいのは **コード差分ではありません**。
会議の議事録から起こした、**まだ spec を書く前のタスク分割案**です。
実装は 1 行も存在しません。審査対象は「この割り方でよいか」だけです。

リポジトリは read-only で読めます。**実ファイルを読んで裏を取ってください。**

## 背景

- 会議の決定事項: `<決まったこと。箇条書き>`
- 期限 / マイルストーン: `<いつまでに何が出ている必要があるか>`
- 依頼者の意向: `<「大改修はしたくない」「まず確定分だけ着手したい」等、明示された制約や好み>`
- 対象リポジトリ: `<リポジトリA>` / `<リポジトリB>` / `<リポジトリC>`
- 台帳の運用: 着手する作業は `task/` に spec + progress を置く。着手しない候補は `backlog/` に置く
  （完了条件は未確定のまま）。今回の振り分けもこの表に含まれています。

## 私が実コードから導いた前提（検証せよ）

以下は **私がコードを読んで導いた前提**であり、**誤っている可能性があります。**
**鵜呑みにしてはなりません。** 1 件ずつ実ファイルで確かめ、誤っていれば根拠となる
ファイルパスと該当箇所を挙げて指摘してください。

1. `<前提。例: 「X という機能は A 系統にのみ実装されており、B 系統には無い」>`
   （確認した箇所: `<path>`）
2. `<前提>`（確認した箇所: `<path>`）
3. `<前提>`（確認した箇所: `<path>`）
4. `<前提>`（確認した箇所: `<path>`）
5. `<前提>`（確認した箇所: `<path>`）

とくに次の型の誤りを疑ってください。

- 「〜という仕組みは存在しない」— **片方の系統しか見ていない**可能性
- 「GUI の設定作業だけでコード差分なし」— 制御コードがリポジトリ内にある可能性
- 「定義 1 箇所で済む」— 同じ定義が複数箇所に散っている可能性
- 「この値を足すだけ」— 未知の値を既定値へフォールバックする**消費側**が別リポにある可能性

## 審査対象の分割案

| # | 台帳 | 作業名 | 対象リポジトリ | 概要 | 完了条件（案） | 依存 |
|---|---|---|---|---|---|---|
| 1 | task | `<名前>` | `<リポジトリA>` | `<何をするか>` | `<検証可能な条件>` | — |
| 2 | task | `<名前>` | `<リポジトリB>` | `<何をするか>` | `<検証可能な条件>` | #1 |
| 3 | backlog | `<名前>` | `<リポジトリA>` | `<何をするか>` | 未確定（昇格時に埋める） | — |

## 審査してほしい観点

1. **前提の事実性** — 上の番号付き前提のうち、実ファイルと食い違うものはどれか
2. **粒度** — 1 件が大きすぎる / 小さすぎるものはどれか。分割・統合の具体案を出す
3. **境界と依存順** — 責務の切れ目は妥当か。依存順に矛盾・循環はないか。
   契約（共有型・API）を先に凍結すべき作業が後ろに来ていないか
4. **抜け漏れ** — 会議の決定事項に対して、この分割で足りていない作業はあるか。
   とくに**変更を消費する下流側**（別リポ・通知・帳票・外部連携）の取りこぼし
5. **台帳の振り分けの妥当性** — `task` / `backlog` の割り当ては、上に書いた**期限**に対して
   妥当か。期限に必要なものが backlog に落ちていないか。逆に不要なものが task にないか
6. **完了条件が検証可能か** — 各完了条件は、実行して真偽を判定できる形か。
   「正しく動くこと」のような判定不能な条件になっていないか。
   実態より誇大な条件（「1 箇所に統合」など）はないか
7. **依頼者の意向との整合** — 「背景」に書いた制約（規模・締切・やりたくないこと）に反する
   提案になっていないか。汎用エンジン化など過剰設計に寄っていないか

## 注意（重要）

- **サンドボックス内でテストや CI を再実行しないでください。** read-only 環境では一時ディレクトリを
  作る検査が `EPERM` で失敗します。それは実装の欠陥ではなく環境要因であり、報告されると
  誤検知になります。合否は依頼側が自環境で実測した結果で判定します。
- ファイルを変更しないでください。`git commit` / `push` もしないでください。
- 推測で断定しないでください。確かめられなかった点は「未確認」と明示してください。

## 出力形式

次の JSON だけを出力してください（前後に地の文を付けない）。

```json
{
  "verdict": "green | yellow | red",
  "summary": "<全体判定の理由を 3 行以内>",
  "findings": [
    {
      "severity": "critical | high | medium | low",
      "category": "前提の事実性 | 粒度 | 境界と依存順 | 抜け漏れ | 台帳の振り分け | 完了条件 | 意向との整合",
      "target": "<対象のタスク番号、または『前提 3』>",
      "claim": "<何が問題か>",
      "evidence": "<根拠となるファイルパスと該当箇所。読んで確かめた事実のみ>",
      "action": "<どう直すか。分割案の具体的な修正>"
    }
  ],
  "carryover": ["<今回の分割の外だが記録しておくべき事項>"]
}
```

判定基準:

- `red` — 前提の誤り、または抜け漏れによって**分割そのものを組み直す必要がある**
- `yellow` — 粒度・完了条件の修正で済む
- `green` — このまま spec 起草へ進んでよい
