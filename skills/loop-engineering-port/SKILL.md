# ループエンジニアリング機構の移植

spec 駆動ループ（1 作業 = spec + progress、完了条件に対する検証、凍結ガード、
Verify 2 段、Stop hook、PR マージ後のアーカイブ）を **別のリポジトリへ持ち込む**ときの手引き。

参照実装は `t2421/simple-loop-engineering`（public、Node）。ここでは
**言語・ホストに依存しない形**で穴と方針を述べる。

---

## 0. 順序

1. **`CLAUDE.md` を先に埋める。** ツールより先。ループを回すのは `CLAUDE.md` であって、
   ツールはそれが要求する検査を機械化しているにすぎない。移植コストの本体もここにある
2. **1 回目は手で移す。共通化しない。** 2 つ目のプロジェクトが存在する前に契約
   （マニフェスト・共通パッケージ）を決めると speculative generality になる。
   手移植のコストは、間違った抽象を後から剥がすコストよりはるかに小さい
3. **工程は減らしてよい。ゲートは減らさない。** e2e・見た目・プレビューは対応物が無ければ省く。
   Verify 2 段 / Critical ゼロ / 凍結ガード / 進捗結合は省かない
4. 書き換えた箇所を **1 件ずつ記録する**。これが 2 回目以降の抽象化の唯一の原資料になる

---

## 1. 何が移植コストか（測り方）

固有語スキャンで当たりを付ける。ただし **2 軸で測る**。

| 軸 | 検索語の例 |
|---|---|
| 言語・ツールチェーン固有 | `npm` / `package.json` / `pytest` / `gradle` / `playwright` |
| **レイアウト固有** | `src/` / `tests/` / `lib/` / 作業ディレクトリ名 |

**片方だけで測ると必ず読み違える。** 参照実装では、言語固有語ヒット 0 のツールが
レイアウト語には依存していた（進捗結合の検査・worktree ガードの「実装ディレクトリ」定数）。
「ヒット 0 = 無変更で動く」は成り立たない。

経験則として、固有性は **十数個の名前付き概念**に凝集する。骨格（判定構造・型・ゲートの配置）は
最初から言語非依存である。だから移植は「書き直し」ではなく「穴埋め」になる。

---

## 2. 穴の一覧と埋め方

### 2.1 検証コマンドの契約 — `command` と `definedIn` の 2 項目

ループの中心は「共通の検証」1 コマンド（例: `npm run ci`）である。移すのは 2 つ。

| 項目 | 意味 |
|---|---|
| `command` | 何を実行するか |
| `definedIn` | **その定義がどのファイルにあるか** |

`definedIn` を移し忘れると凍結が空洞化する。凍結の本質は
「**検証コマンドの中身を書き換えて検証を弱めることを止める**」ことであり、
コマンド名だけを守っても定義ファイルを書き換えれば回避できる。

| 移植先 | command の例 | definedIn の例 |
|---|---|---|
| Node | `npm run ci` | `package.json` の `scripts` |
| Python | `make ci` / `uv run task ci` | `Makefile` / `pyproject.toml` |
| Swift | `make ci` / `swift test` | `Makefile` / `Package.swift` |
| Go | `make ci` | `Makefile` |
| Gradle | `./gradlew check` | `build.gradle(.kts)` |

判断基準は 1 つ: **そのファイルを書き換えると検証が弱まるか。** 弱まるなら凍結する。

定義の取り出しは 1 関数に閉じ込める。JSON でない形式（Makefile 等）はパースせず
**ファイル内容の同一性**で判定してよい。**緩い側ではなく強い側に倒す。**

### 2.2 実装ディレクトリの名前

「触ったら実装変更とみなす場所」の一覧。次の 2 か所で使う。

- 実装 PR に progress 更新を要求する検査
- プライマリチェックアウトでの実装編集をブロックする hook

**ソースだけでなく、テストと "ループのツール自身" を含める。** ツールを外すと、
ゲートを緩める変更が進捗の記録なしに入る。ビルド生成物は入れない。

### 2.3 依存導入コマンド

worktree を作った直後に打つ 1 コマンド（`npm ci` / `uv sync` / `bundle install` /
`go mod download` / `swift package resolve`）。

基準: **新しい worktree でその 1 コマンドを打てば検証が走る状態になるか。**
不要な言語では **呼び出しごと落とす**。空コマンドを置かない。

### 2.4 テストの列挙

ランナーが自動発見しない言語（Node の `node --test` 等）でだけ必要になる補助である。
pytest / `go test ./...` / `swift test` / JUnit のように **ランナーが自前で発見するなら要らない**。
消して検証コマンドから直接ランナーを呼ぶ。

残す場合の基準: **新しいテストを足したとき、別ファイルへの登録忘れで黙って実行されない**
状態を作らないこと。登録忘れが検知されない列挙は、検証を弱める穴である。

### 2.5 条件付き工程（e2e・見た目・プレビュー）

**省略可能な工程であって、プラグイン枠ではない。** 移植先に UI が無いなら**ファイルごと消す**。
常に false を返す判定や、何も見ないレビュアー定義を置かない。
「存在するが何もしない」形で残すと、後で本当に必要になったとき
「すでにある（ように見える）」ため誰も作らない。

作る場合の設計基準は 2 つ。

- **発火条件は差分のパスで決める。** 重い工程を回すか間引くかを人間の裁量にしない
- **判定コードは base リビジョン側を実行する。** 候補側（PR のマージコミット）で判定すると、
  「判定を常に false にする変更」と「実装変更」を同じ PR に入れるだけで工程を間引ける。
  この仕掛けは移植先でもそのまま持ち出す（→ 2.6 のチェッカーにも同じ話が効く）

### 2.6 保護対象（凍結）の再定義 — 移植で最も間違えやすい

基準は 1 つだけ。

> **それを書き換えれば停止条件を「達成」できてしまうか。**

該当は 4 種類。移植先でこの 4 つを洗い直す。

1. **期待値** — spec の完了条件、テストの期待値、デザイントークン表、デザイン抽出物
2. **検証コマンドの定義** — 2.1 の `definedIn`
3. **ゲートの判定コード** — **チェッカー自身を筆頭に含める**。外すと 2 PR で恒久的に無効化できる
   （1 本目でチェッカーを骨抜きにし、マージ後は骨抜き版が base になる）
4. **型** — spec / progress のテンプレート。見出し名・順番が変わると lint が意味を失う

移植先で足すもの: ビルド定義・lint 設定・CI 設定が別ファイルなら、それらも保護に足す。

**落とし穴: `CLAUDE.md` の「変えてはいけないもの」に行を足しただけではガードは検知しない。**
判定コード側の一覧に足すまでが 1 セットである。人間向けの一覧と機械の判定を必ず対にする。

人間による例外の経路（PR ラベル等）も移す。ホストに対応物が無いなら **例外を無くす**側に倒す。
「例外を申請できない」は不便だが、「例外が黙って通る」は検証の破綻である。

### 2.7 モデルルーティング（Complexity → モデル）

等級（S / M / L）の意味は不変。**対応先のモデル名だけが時期とプロジェクトに依存する。**
基準は「実装 1 件あたりの**設計判断の量**」であってコード行数ではない。

- S: 単一ファイルの小変更・定型作業
- M: 複数ファイルにまたがる通常の機能追加・修正
- L: 設計判断・凍結改訂・横断的変更

等級付けは spec 起草時に 1 回だけ行い、以後は表引きにする。確率論的な判断を 1 点に隔離し、
**表そのものの変更はコード変更として PR レビューを通す**（会話ごとの裁量にしない）。

### 2.8 レビュアー（Verify 外部）

不変なのは **「実装したのと別の視点が Critical ゼロを宣言するまで完了にしない」** という構造であって、
特定のエージェント名でも特定の CLI でもない。移植先で決めるのは 3 つ。

- **別視点をどう用意するか**（別モデル / 別 CLI / 人間）
- **重大度の語彙**（Critical / High / Medium / Low）と、何がブロッキングか
- **レビュアーはサンドボックス内で検証を再実行しない。** read-only サンドボックスでは
  一時ディレクトリを作るテストが `EPERM` で落ち、それは実装の欠陥ではなく環境要因である。
  その切り分けと釈明が出力とトークンを浪費する。**合否は親が貼った実測結果で判定する**

3 点目は言語に関係なく効く。エージェント定義に必ず書き写す。

### 2.9 ホストの前提（PR とチェック）

ホスト依存は **2 つの問い合わせ**に閉じている。

- **その PR はマージ済みか**（アーカイブの前提条件）
- **HEAD のチェックはすべて緑か**（Stop hook が「赤いまま完了と言う」ことを止める）

GitHub 以外（GitLab / Forgejo / 社内 Gerrit）へ移すなら、この 2 関数だけ差し替える。

既定ブランチ名も穴である。worktree を切る元が `main` 固定なら、`master` のリポジトリでは
**作業開始が毎回失敗する**。

### 2.10 hook と権限

構造（編集前にブロック / 停止時に検証と CI 結果を確認）は不変。差し替えるのは
**検証コマンドと許可リストの語彙**だけ。

- **timeout は移植先の CI の実測時間から決める。** 短すぎる timeout は Stop hook を
  「たまに落ちる邪魔なもの」にし、必ず無効化される。**検証が重いなら timeout を伸ばす。検証を削らない**
- 許可リストを移植先のコマンド名に置き換える。非対話実行では許可リストに無いコマンドが
  黙って拒否され、エージェントが「何もしない」ように見える

### 2.11 lint の型と固定文字列

spec の見出し・progress のメタ情報・Status の語彙・作業ディレクトリ名のパターン。

- 見出しの**名前**は翻訳してよいが、**数と順番と役割は変えない**。とくに
  **「完了条件」を落とさない**。ここが検証の宛先であり、無い spec は incomplete である
- 作業ディレクトリ名のパターンを**絞りすぎない**。ID だけを制約し、slug の文字種は
  「開始 / アーカイブ / lint」の 3 者で**同じ広さ**に揃える。狭い側に寄せると
  「開始はできるが lint だけ落ちる」作業が生まれ、そのリポジトリの全 PR が緑にならなくなる
- **移植元の "歴史的例外リスト" は必ず空にする。** 移植元には
  「規約が固まる前に書かれたので免除する」種類の例外がある。持ち込むと
  **最初から抜け穴を開ける**ことになる

### 2.12 `CLAUDE.md` — 穴と不変の分離

移植コストの本体。**埋める穴**と**書き換えてはいけない原則**を分けて扱う。

埋める穴:

| 穴 | 決め方 |
|---|---|
| ディレクトリ表 | 2.2 と揃える。移植元の遺物ディレクトリの行は落とす |
| 共通の検証 | 2.1 の `command` |
| 見た目・e2e の節 | 対応物が無いなら**節ごと落とす** |
| デザインの正（Figma 等） | デザインの正が別物なら書き換える。無ければ落とす |
| レビュアー名 | 2.8 |
| 変えてはいけないもの | 2.6 で洗い直す |
| コーディング規約 | 移植先の言語の規約に置き換える |
| PR への画像添付手順 | ホストが変わるなら差し替える |

**書き換えてはいけない（不変の原則）:**

- 開発ループの工程と順番（Plan → Implement → Verify(自己) → Verify(外部) → Fix → Record → Archive）
- **Critical が残っている状態で「完了」と報告しない。Status を Done にしない。アーカイブもしない**
- **実行したコマンドの出力を、要約せずに会話に貼る**（「確認した」ではなく「確認した結果」）
- **停止条件を満たすために期待値・検証コマンド・ゲートを書き換えない**
- コミットとマージの規律（spec/progress は docs PR に分ける／アーカイブは既定ブランチへ直接）
- 1 worktree = 1 作業 = 1 ブランチ
- トークンコストの規律（レビュアーに渡すのは差分・対象 spec・実測結果だけ。往復に上限を置く）

これらは言語にもホストにも依存しない。**移植で最初に削られやすく、削ると
ループが「動いているように見えて何も検証していない」状態になる。**

### 2.13 持ち出さないもの

- 移植元のアプリ本体と、そのテスト
- 移植元の作業履歴（アーカイブ済みの spec/progress、backlog）
- 移行前の遺物ディレクトリとその互換シンボリックリンク
- 移植元固有の gitignore 行

**持ち出す**のは **ループのツール自身のテスト**である。ゲートを移してテストを置いていくと、
**移植先ではゲートが正しく効いているか誰も確かめていない**状態になる。
定数を差し替えたら、対応するテストの期待値も同じ PR で直す。

## 3. 受け入れ確認

移植が終わったかは、**実際の出力で**示す。自己申告にしない。

1. 検証コマンドが緑（出力を貼る）
2. docs lint が、移植した空の作業ディレクトリ構造で緑
3. 次の ID の採番が `0001` を返す
4. **わざと落とす検査:** 保護パスを 1 行変える PR を作り、ガードが赤くなる。
   例外ラベルを付けると緑になる
5. **わざと落とす検査:** 実装ディレクトリを触って progress を更新しない PR を作り、
   進捗結合の検査が赤くなる
6. Stop hook が、意図的に壊した検証で実際にセッションを止める

4〜6 を飛ばさない。**ゲートは「置いた」ことではなく「落ちること」で確認する。**
移植直後のゲートは、定数の差し替え漏れで **常に通る**状態になりやすい。

## 4. アンチパターン

- **空実装で工程を残す。** 常に false を返す判定、何も見ないレビュアー定義。
  「すでにある」ため誰も作らない
- **人間向けの凍結一覧に行を足して終わる。** 判定コード側に足すまでが 1 セット
- **チェッカー自身を保護対象から外す。** 2 PR で恒久的に無効化できる
- **候補側の判定コードを CI で実行する。** 判定を骨抜きにする変更と実装変更を
  同じ PR に入れれば回避できる
- **timeout や検証の重さを理由に Stop hook を外す。** 伸ばす側に倒す
- **移植元の歴史的例外リストをそのまま持ち込む。** 最初から抜け穴を開ける
- **1 回目の移植で共通化する。** 実測前の抽象は剥がすコストのほうが高い
