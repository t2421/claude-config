# 非対話エージェントの権限詰まり

## 症状

人間から見た症状はどれも「**エージェントが仕事をしていない**」に見える:

- チャットに返事が来ない（メッセージ送信コマンドだけが落ちている）
- 「やりました」と言うのに成果物が無い
- タスクの途中で理由も言わず止まる

実際にはエージェントは正しく動いていて、**特定のコマンドだけが実行前に弾かれている**ことが多い。

## 原因

`~/.claude/settings.json` の `permissions` を**許可リスト方式**で運用していると:

```json
{
  "permissions": {
    "allow": ["Read", "Bash(git status*)", "Bash(ls*)", "..."],
    "defaultMode": "auto"
  }
}
```

- **対話セッション**なら、リストに無いコマンドは確認ダイアログが出て、人間が「許可」を押せる
- **非対話セッション**（headless / don't ask モード）は**押す人間がいないので、ダイアログを出さずに即拒否**する

つまり同じ設定でも、対話なら「ちょっと待って」で済むものが、非対話では**恒久的な機能欠損**になる。
新しい CLI をエージェントに渡したのに allow へ追記し忘れる、が典型。

さらに悪いことに、**エージェントは自分ではこれを直せない**:

- `settings.json` を Edit しようとしても、config-protection 系フックや同じ許可リストで拒否される
- 自分の許可範囲を自分で広げられるなら、そもそも許可リストの意味が無い（**これは正しい設計**）

→ 原因を特定して**人間に頼むまでが、エージェント側にできる全て**。だから特定の速さが全て。

## 切り分け（30秒）

**許可済みと確信できるコマンドと、疑っているコマンドを並べて実行し、結果の差を見る。**

```bash
which <cmd>        # ✅ 通る → 許可リスト機構そのものは生きている / バイナリも存在する
<cmd> <無害な読み取り操作>   # ❌ 拒否 → <cmd> が allow に無いことが確定
```

`which *` は多くの設定で許可済みなので基準に使いやすい。この2つを比べれば:

| `which` | 本体コマンド | 結論 |
|---|---|---|
| ✅ | ✅ | 権限は問題ない。別の原因（認証・ネットワーク・引数）を見る |
| ✅ | ❌ | **許可リスト漏れ確定**。バイナリ欠損でもネットワーク不通でもない |
| ❌ | ❌ | インストールされていない。パスを確認する |

拒否メッセージは環境によって「サンドボックス」「権限」など曖昧な表現になるので、
**メッセージを読むより、この2行を実行したほうが速く確実**。

### やりがちな遠回り

- サンドボックス無効化オプションを試す → 許可リスト漏れなら同じく拒否される。切り分けにならない
- バイナリのパスや環境変数を疑う → `which` が通った時点で否定できる
- 設定ファイルを自分で書き換えようとする → 拒否される。時間の無駄

### 「編集したよ」と言われたのに直っていないとき

**ファイルを読み直して、実際に追記されているか自分の目で確認する**。別のファイル
（`settings.local.json` / プロジェクト側の `.claude/settings.json` / アプリ独自の設定）を
編集していた、というのが最も多い。読んで無ければ、**どのパスに何行目として入れるべきか**を
具体的に示す。「allow に追加して」だけでは同じ失敗を繰り返す。

## 対処（人間側の作業）

`permissions.allow` に追記する。**用途を絞って狭く書く**:

```json
"Bash(<cmd> <読み取り系サブコマンド>*)",
"Bash(<cmd> <会話・記憶系サブコマンド> *)"
```

`"Bash(<cmd> *)"` の1行で全部許すのが手軽だが、その CLI が
**外部に成果物を作る操作**（リポジトリ作成・PR/Issue 発行・SNS 投稿・デプロイ）を
含む場合は分けて考える。必要になった時点で足すほうが安全。

反映されたかは、拒否されていたコマンドをもう一度実行して確認する。
稼働中セッションにそのまま効くこともあれば、再起動が要ることもある。

## 許可リストを新規に書くときの設計指針

非対話で走らせる予定があるなら、**「後で許可を押せばいい」は成立しない**前提で書く:

1. **そのエージェントの存在意義に直結するコマンドを最初に入れる。**
   チャットで応答するエージェントならメッセージ送信系、
   デプロイするエージェントなら配信コマンド。ここが抜けると存在ごと無意味になる
2. **読み取りは広く、書き込みは狭く。** 状況把握が封じられると、
   エージェントは推測で動くか黙るしかなくなる
3. **外部に出るもの（公開・課金・不可逆）は明示的に分ける。** 一括許可に混ぜない
4. **新しい CLI をエージェントに渡したら、その場で allow も更新する。** セットで扱う

## 派生

同じ構造は Claude Code の設定に限らない。**「人間の承認を前提にした仕組み」を
「人間がいない実行経路」に流用したとき**に一般的に起きる:

- cron / CI で走らせたエージェント
- サブエージェント（親の対話性を継承しない）
- 対話ログインが必要な MCP サーバーを headless 実行で使う
  （→ 認証済みのはずが繋がらない。ログインは対話セッション側で済ませておく）

いずれも共通の対処は同じ: **人間がいる経路で事前に承認を通しておく**。
