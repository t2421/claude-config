# 議事録からタスクを切り、台帳へ落とす

会議で決まったことを、spec 駆動リポジトリの台帳（`task/<id>-<slug>/spec.md` + `progress.md`、
着手しない候補は `backlog/`）へ落とすまでの手順。

**最大の分岐点は「議事録の言葉でタスクを切らないこと」である。** 議事録は人間の記憶と要約で
できていて、実装の状態とは体系的にずれる。ずれたまま切った分割は、粒度も依存順も完了条件も
まとめて外れる。

---

## 原則: 議事録の言葉でタスクを切らない。コードで裏取りしてから切る

議事録に出てくる「〜の仕組みはもうできている」「あとは設定するだけ」「〜するフラグを立てる」は、
実装では次のどれかであることが多い。

| 議事録の言い方 | 実装での実態 |
|---|---|
| 「もうできている」 | **条件付き**で動く（別の入口・別のロールでは動かない） |
| 「もうできている」 | 名前が同じだけの**別物**（似た概念の専用実装が 2 系統ある） |
| 「設定するだけ」 | 設定画面を制御する**コードがリポジトリ内にある**（識別子がハードコード） |
| 「1 箇所直せば済む」 | 同じ定義が**複数箇所**に散っている |

裏取りは高価ではない。**grep 一発**で覆る見積もりがほとんどである。切る前に必ず、
タスク 1 件につき「この前提はどのファイルの何行目で確かめたか」を言えるようにする。

---

## 手順

### 1. 粒度をユーザーと対話で決める（台帳を書き始める前）

いきなり台帳を書かない。**最初に決めるのは分割そのものではなく、分割の物差し**である。
次の型で選択肢を出して選ばせる。

- **粒度**: 「PR 単位まで割る」／「領域まとまり単位で 1 件にする」／
  「確定している分だけ PR 単位、未確定は粗いまま」
- **範囲**: 今回どこまで起票するか（今期の期限に間に合わせる分だけか、先の分も置くか）
- **未確定の設計の扱い**: `task/`（着手する）に置くか `backlog/`（候補のまま）に置くか

この 3 つが決まっていないと、後段のレビューで「粒度が粗い/細かい」という指摘が来ても
判定できない。物差しが無い指摘は受けようがない。

### 2. 実コードで裏取りする

議事録の各項目について、対応する実装を実際に読む。読んだ結果を**前提のリスト**として
番号付きで書き出す。この番号付きリストが、そのまま次段のレビュー依頼に入る。

裏取りで特に狙う点は [見積もりの罠](#見積もりの罠) を参照。

### 3. 分割案をクロスモデル・レビュアーへ渡す

別モデルの CLI（[`codex-sol`](../codex-sol/SKILL.md) 参照）に、**まだ spec を書く前の分割案**を
審査させる。掛け方は [クロスモデルレビューの掛け方](#クロスモデルレビューの掛け方) を参照。

### 4. 指摘を選別して反映する

**レビュアーも鵜呑みにしない。** 詳細は [レビュー結果の扱い](#レビュー結果の扱い) を参照。

### 5. 台帳化して docs PR にする

分割が固まってから spec / progress を起草する（並行起草するなら
[並行起草の運用](#並行起草の運用)）。実装 PR とは混ぜず、**docs PR 単独**で先に main へ入れる。

---

## クロスモデルレビューの掛け方

雛形は [`templates/cross-model-review-prompt.md`](templates/cross-model-review-prompt.md)。
穴を埋めればそのまま渡せる。

核心は 1 点だけである。

> **自分がコードから導いた前提を番号付きで列挙し、「検証せよ・鵜呑みにするな」と明記する。**

レビュアーは read-only サンドボックスで実ファイルを読めるので、前提の真偽を自分で確かめられる。
前提を隠して分割案だけ渡すと、レビュアーはこちらの誤りを前提ごと受け継いでしまい、
**独立審査にならない**。分割の誤りの多くは前提の誤りに由来するので、ここを開示するかどうかで
レビューの価値が決まる。

あわせて必ず入れるもの:

- **背景**（会議の決定事項・期限・依頼者の意向）。これが無いと「抜け漏れ」を判定できない
- **審査観点を箇条書きで固定する**（7 観点。テンプレート参照）
- **出力形式の指定**（verdict / summary / findings / carryover のような構造化。
  スキーマを強制すると、指摘の重みを機械的に選別できる）

### 「サンドボックス内でテストや CI を再実行するな」と必ず書く

read-only サンドボックスでは、一時ディレクトリを作る検査が `EPERM` で落ちる。
これは**実装の欠陥ではなく環境要因**であり、そのまま報告されると誤検知として混ざる。
合否は依頼側が自環境で実測した結果で判定する、と明記して禁じておく。

## レビュー結果の扱い

**レビュアーの指摘も鵜呑みにしない。** ただし無視もしない。基準は 1 つ。

> **分割を変える重みのある指摘だけ、自分で実ファイルを開いて検証する。**

「文言をこう直せ」程度は読んで判断すればよい。「この前提は誤り」「このタスクは 2 つに割るべき」
「この対象リポジトリが抜けている」は、分割そのものが変わるので必ず自分で確かめる。

そして、**実際に自分の前提のほうが間違っていることがある**。典型は次の形である。

> 「〜という概念はこのシステムに存在しない」と断定したが、それは**新しい方の実装**にしか
> 当てはまらず、**古い方の実装には既に同等の仕組みが稼働していた**。

これは字面の細部ではなく、**設計判断が「更地に作る」か「既存の穴埋め」かを逆転させる**誤りだった。
片系統だけを読んで「存在しない」と断定していないか、系統が 2 つ以上あるシステムでは常に疑う。

## 見積もりの罠

裏取りのときに具体的に狙う点。いずれも実際に外した箇所を一般化したものである。

### 「GUI 設定作業だからコード差分なし」は grep してから言う

外部 SaaS や管理画面の設定作業に見えるものでも、**その画面・フォームを制御するコードが
リポジトリ内にある**ことがある。しかも対象ごとの識別子がハードコードされていたりする。
作業の見た目の種別だけで「コード差分なし」と書かない。まず grep する。

### 種別・区分の値を足すタスクは、未知の値のフォールバック実装を下流に探す

新しい種別（区分・カテゴリ・プランなど）の値を足すタスクは、**その値を消費する側**を全部探す。
特に危ないのは、**未知の値を既定値へフォールバックする実装**である。

- 例外にならないので**テストも通る**
- 静かに誤った内容が出力される（通知メール・帳票・外部連携など、顧客の目に届く出口ほど痛い）

対象リポジトリの取りこぼしはここで起きる。「値を足す」タスクは、値の**定義側**ではなく
**消費側**を数えてから見積もる。

### 「定義 1 箇所で済む」と書く前に、同じ定義が何箇所にあるか数える

リファクタタスクの完了条件で最も誇大になりやすいのがこれ。数えたら 5 箇所に散在していた、
というのは珍しくない。全部を 1 箇所に寄せられないなら、完了条件を
**「そのうち 2 箇所に限定する」のように現実の数へ合わせて明記する**。

達成できない完了条件を書くと、検証の段で「達成扱い」にする圧力が生まれる。台帳の信用が落ちる。

### レビュー中に見つかった「現時点で成立している問題」は独立タスクにする

裏取りやレビューの過程で、当初の依頼と無関係な既存の欠陥が見つかることがある。

> 一覧 API は所属で絞られるのに、詳細取得 API は ID 直引きで同等の検査が無かった。

これは「将来の要件」ではなく**今この瞬間に成立している問題**である。将来要件のタスクに
混ぜ込むと、要件の可否と一緒に握り潰される。**独立したタスクとして切る。**

## 設計の原則: フラグを足すな、値を取る属性にしろ

議事録では「◯◯フラグを立てる」で合意されがちだが、そのまま実装すると、似たケースが来るたびに
boolean を足し続けることになる。分割の段階で次の 5 点に照らして設計を上げておく。

1. **boolean を足す設計は「次元（列）が増える」。値を取る単一属性にすれば「値（マスタの行）が
   増える」だけになる。** 増える方向を、スキーマ変更からデータ追加へ移す。
2. **派生できるものは持たない。** 既に持っている識別子から**導出**し、対応をマスタ化すれば、
   新しい種別が来てもコードも列も変わらない。ハードコードした if / switch にしない。
3. **1 対多の「多」の側に持たせる。** 一側（例: ユーザー）に単一値を持たせると、多側
   （例: 所持デバイス）が複数になった時点で破綻する。多側に持たせ、一側は多側経由で辿る。
   副産物として「登録を中断したらフラグが付かない」類の懸念が**そもそも問題でなくなる**。
4. **性能上どうしても非正規化が要るなら、正は導出規則、コピーは再構築可能な派生値とする。**
   バックフィル手順を持つことを条件にする。手で維持する boolean にしない。
5. **既存の似た仕組みがあるなら、それを特殊形として含む一般形にする。**
   ただし**汎用ポリシーエンジンは作らない。** 締切と「大改修したくない」という要求に反する。
   一般形とは「今ある 2 ケースを 1 つの規則で書ける」程度を指す。

## 並行起草の運用

台帳が 10 件を超えると、サブエージェントへ並行起草させたくなる。次の 4 点を守る。

- **共通の背景を 1 つのファイルに書き、全エージェントにそれを読ませる。** 同じ文脈を N 回
  プロンプトへ貼らない。ファイルには**実ファイルで裏取り済みの事実**を列挙し、
  **推測で上書きするなと明記**する
- **各エージェントに触ってよいパスを明示的に割り当てる**（同一ブランチ・同一チェックアウトで
  走らせる場合はとくに必須）
- **git 操作（`add` / `commit` / `mv`）は親だけが行う。** サブエージェントが `git status` 全体を
  根拠に判断すると、他のエージェントの途中生成物を巻き込んでコミットする
- **並行中に docs lint が赤くなるのは正常。** ディレクトリだけ作られて中身が空の瞬間が生まれる。
  **全ファイルが揃ってから判定する**（途中の赤を見て修正に入ると、書きかけを壊す）

## 環境の罠

- **macOS には `timeout` コマンドが無い**（`command not found`）。`gtimeout`（coreutils）か、
  **回数上限付きの `until` ループ**で代替する
- エージェントのフォアグラウンド `sleep` は塞がれていることがあるが、`sh -c '...sleep...'` の
  ネストなら通ることがある。いずれにせよ**待機には必ず回数上限を付ける**（無限待機にしない）
